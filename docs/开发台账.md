### 2026-09-27 · 我的修复语句写错了：identities 唯一约束冲突

**本轮最值得记的一段：一个被自己实测推翻的推断**

起初查 RLS 策略时发现 `orders_select` 用的是 `can_see_order(orders.*)`，函数体要读
`customer_id` / `shop_id` / `rider_id` / `status` 四列；于是推断「Realtime 在默认 replica identity 下，
UPDATE 的旧记录只带主键，判不了 RLS，事件会被静默丢弃」，并据此在 migration 里加了
`REPLICA IDENTITY FULL`。**第一次探测恰好支持了这个推断**：订阅成功后立刻改一笔订单，10 秒内没收到推送。

但这个证据不干净——为了排除"通道本身就不通"，写了 `scripts/verify-realtime.mjs` 做对照实验：
先往 `notifications` 插一条（这张表的读策略只看 `user_id`，事件一定能送；页面不读该表，插完即删），
确认通道是通的，再测订单更新。结果**订单更新也收到了**，而且事件载荷里 `old` 只有 `id`
——正说明用的就是默认 replica identity。再换成两个账号互测（顾客改单、商家端订阅），同样两端都收到。
回头看，第一次失败更像是"订阅刚建立那一小段时间的事件投递时序"，第二次起每次都能收到。

**结论**：跨端更新推送在默认 replica identity 下就能工作，`REPLICA IDENTITY FULL` 并非必需；
本项目收到推送后一律重新查库、不读事件载荷，加 FULL 只增加 WAL 体积、没有收益。
据此把 migration 收窄成只做下面这一件事，文件名也改成与内容相符的 `..._realtime_conversations.sql`。

**真正需要补的那一处**：init 脚本的 publication 覆盖了 orders / order_items / messages /
notifications / refund_requests / delivery_exceptions，**唯独漏了 conversations**。
没进 publication 的表，变更事件根本不会发出——"对方把会话标记已读、或新建了一个会话"就不会实时刷新。
migration 只做这一件事（幂等写法，可重复执行）。

**另一处必须守住的细节：实时刷新不能覆盖本地还没写库的改动**

原来的"登录后拉一遍"是**数据库无条件覆盖**同名订单/会话。加了实时推送后这个规则会出事：
商家刚点"接单"（本地已更新、写库还在路上），此时推来一个事件触发重拉，
就会把界面弹回旧状态；更糟的是本地改动会被判定为"已同步"，**再也写不回去**。
处置：合并前先快照"已同步基线"，实时刷新时对**有本地未写库改动**的订单/会话以本地为准；
登录/换账号的首次拉取仍维持"以数据库为准"的原行为（否则跨设备会拿旧本地数据去覆盖新状态）。

### 2026-09-28 · 浏览器端到端首次验收：修掉两个真机才暴露的 bug（提交 `c7c24d3`）

**背景**：用户按交接文档做"两个窗口观感验收"。实时推送这半边是好消息——顾客下单后商家端不刷新就看到；
但同时也暴露出两个问题：① 点 1 份菜，两端都显示"好几份"；② 商家端「商品管理」一直停在"店铺数据加载中"。
这两个都是纯接口验证发现不了的 UI 接线问题，正好印证交接文档里"尚未验证：浏览器端到端"那一栏。

**Bug ①：订单明细被重复写入**

- 现象：一笔订单在数据库里被写成几十上百条一模一样的 `order_items`，顾客端与商家端显示成一长串同样的菜。
- 取证：按订单统计明细行数 → ORD000055 **4 条**、ORD000037 **96 条**、ORD000003 **192 条**；
  三笔订单的 `total_amount` 都等于"1 份"的价格，说明金额是对的、只有明细行被复制。
  间隔 30 秒再查一次，行数不再增长（循环只在页面开着时跑）。
- 根因：`orders-remote.ts` 的 `upsertOrder()` 里，明细段注释写着"新订单才需要插入；已存在则跳过"，
  **但代码没有跳过**——每次回写都 `insert(rows)` 一遍。而 `order_items` 在本项目里是"下单快照、不可改"
  （RLS 只有 `select` / `insert`，没有 update / delete），表上也没有 `(order_id, sort)` 唯一约束，
  于是每次回写都新增一批行；"写库 → Realtime 推送 → 重拉 → 再次判为待写"的循环还会把它放大成倍增长。
- 修复：**只在新订单时写明细**（`orders.insert` 没报冲突才是新订单）；老订单只在"库里确实一条明细都没有"时
  补写一次，覆盖"orders 插成功但明细没写上"的极端情况。

**Bug ②：商家端「商品管理」永远停在"店铺数据加载中..."**

- 取证一（数据侧）：用商家账号直接查库，9 家店 / 62 道菜 / 自己的店铺（`00000000-…-0099` 演示小店）都能查到
  → 数据与 RLS 都正常，问题在前端加载时机。
- 取证二（复现）：新增 `scripts/e2e-merchant.html`，用无头浏览器真实走"商家端 → 登录 → 商品管理"，
  修复前该页只显示"店铺数据加载中..."。
- 根因：只有顾客端页面（`HomePage` / `SearchPage` / `ShopDetailPage`）调用 `useShops()`，
  而 `useShops()` 才是触发 `ensureShopsLoaded()` 的地方；**商家端页面一律只调 `getAllShops()` + `useShopStatus()`**，
  没有任何触发点 → `remoteShops` 始终为 null → `getAllShops()` 回退到内置演示店铺（id 是 `'1'`~`'8'`）
  → 商家自己的 uuid 店铺找不到 → 页面永远停在"加载中"。
- 修复：`useShopStatus` 登录后触发一次 `ensureShopsLoaded()`（幂等；一次修复覆盖所有商家端页面）；
  另外 `MerchantDishesPage` 在"数据已加载却找不到店铺"时给出明确提示，不再无限转圈。

### 2026-09-28 · 修复「商家拒单不生效」（用户反馈第二个 bug）

**现象（用户原话）**：商家拒单之后订单还会在、顾客端不会显示任何东西、并且仍然显示待接单。

**取证过程**

1. 用商家账号直接查库：4 笔订单**全部还是 `pending`**，其中被拒的那笔 ORD000084 只有 `reject_reason=食材不足`。
   → 说明"状态没改成 rejected"，但"拒单原因写进去了"，是条畸形数据。
2. 对照实验（决定性）：
   - 商家 `insert` 同一行订单 → `error.code = 42501`（new row violates row-level security policy）
   - 顾客 `insert` 同一行订单 → `error.code = 23505`（duplicate key）
   - 商家 `update` 该行 → 成功返回 1 行
3. 真浏览器复现（新增 `scripts/e2e-reject.html`）：点"拒单 → 食材不足 → 确认拒单"后，本机订单状态也未变化。

**两个叠加的根因**

- **根因 A（写库路径断了）**：`upsertOrder` 沿用 2c 的「先 INSERT，遇 23505 再 UPDATE」。
  但 `orders` 的 INSERT 策略只放行顾客（`customer_id = auth.uid()`），商家插入会先撞 **RLS 42501**，
  代码把它当成"写失败"直接 `return false` —— **UPDATE 永远执行不到**。
  也就是说：商家接单 / 拒单 / 出餐在浏览器里**从来就没写进过数据库**
  （`refund_requests`、`delivery_exceptions` 同样的策略形态，店主的售后处理/异常处理同理写不进去）。
- **根因 B（状态被改回去）**：`normalizeOrder` 的状态白名单写成
  `['pending','preparing','ready','picked','delivering','delivered','cancelled']`，
  **漏了 `rejected`（也漏了 `pending_payment`）**，不在名单里的一律按 `pending` 处理。
  而 `merchantReject()` 会调 `notifyOrdersChange()` → 监听器重新读本机订单 → `normalizeOrders` 把
  `rejected` **改回 `pending`**（`rejectReason` 保留）→ 再被写回数据库。
  这同时解释了用户看到的三个现象：订单还在、仍显示待接单、顾客端什么也没有。
  （附带影响：`pending_payment` 也会被改成 `pending`，导致"待支付 15 分钟超时自动取消"永远不触发。）

**修复**

1. `orders-remote.ts`：新增 `upsertByKey(table, row, keyColumn, keyValue)`——**先按 key 列 UPDATE，
   返回 0 行再 INSERT**；INSERT 撞 23505（刚好被别端插进去）则再 UPDATE 一次。
   `orders`（按 id）、`refund_requests`（按 order_id）、`delivery_exceptions`（按 id）三处统一改用它。
2. `useOrders.ts`：把状态白名单抽成 `ALL_ORDER_STATUSES`（9 态，与数据库枚举一一对应）并补全
   `pending_payment` / `rejected`；遇到未知状态改成 `console.warn`，不再静默改写。
3. 新增回归脚本 `scripts/e2e-reject.html`（无头浏览器真实跑拒单 + 顾客端校验），
   runner 也支持了 "只跑指定测试页/角色"：`node scripts/e2e-smoke.mjs scripts/e2e-reject.html merchant`。

### 2026-09-28 · 三个反馈修复：支付/抢单提示误报、到店自取走配送

**用户反馈**：① 到店自取为什么会配送；② 支付明明成功，下方弹支付失败；③ 骑手抢单提示"已被抢走"，但实际抢到了。

**②③ 同一个根因：把结果写在 setState 的更新器里，再 return——而更新器是延后执行的**

```ts
let result = null
setOrders(prev => { ...; result = 新订单; return 更新后的列表 })
return result          // ← 更新器还没跑，这里永远是 null
```
`payOrder` / `riderClaim` / `advanceToStatus` 等 20 来处都是这个写法，调用方拿到 null 就以为失败：
- 收银台：`if (!paid) { toast.error('支付失败，请重试'); return }` → 明明支付成功却报失败，而且**不再跳转成功页**；
- 抢单大厅：`if (result) 成功 else toast.error('手慢了，订单已被抢走')` → 明明抢到却报失败。

**修复**：把 `setOrders` 包一层，自己先同步算出新列表再交给 React（`ordersRef` + 包装函数）。
所有既有函数的返回值立刻变准，20 来处调用点一行都不用改。

**① 到店自取却走配送**

- 根因：结算页的「到店自取」只是把收货地址写成「到店自取」，**订单本身没有自取标记** →
