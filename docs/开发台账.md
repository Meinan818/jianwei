### 2026-09-27 · 我的修复语句写错了：identities 唯一约束冲突

**现象**：用户重跑 seed 报

**本轮最值得记的一段：一个被自己实测推翻的推断**

起初查 RLS 策略时发现 `orders_select` 用的是 `can_see_order(orders.*)`，函数体要读
`customer_id` / `shop_id` / `rider_id` / `status` 四列；于是推断「Realtime 在默认 replica identity 下，
UPDATE 的旧记录只带主键，判不了 RLS，事件会被静默丢弃」，并据此在 migration 里加了
`REPLICA IDENTITY FULL`。**第一次探测恰好支持了这个推断**：订阅成功后立刻改一笔订单，10 秒内没收到推送。

但这个证据不干净——为了排除"通道本身就不通"，写了 `scripts/verify-realtime.mjs` 做对照实验：
先往 `notifications` 插一条（这张表的读策略只看 `user_id`，事件一定能送；页面不读该表，插完即删），
确认通道是通的，再测订单更新。结果**订单更新也收到了**，而且事件载荷里 `old` 只有 `id`
——正说明用的就是默认 replica identity。再换成两个账号互测（顾客改单、商家端订阅），同样两端都收到。
回头看，第一次失败更像是"订阅刚建立那一小段时间的事件投递时序"，第二次起每次都能收到。

**结论**：跨端更新推送在默认 replica identity 下就能工作，`REPLICA IDENTITY FULL` 并非必需；
本项目收到推送后一律重新查库、不读事件载荷，加 FULL 只增加 WAL 体积、没有收益。
据此把 migration 收窄成只做下面这一件事，文件名也改成与内容相符的 `..._realtime_conversations.sql`。

**真正需要补的那一处**：init 脚本的 publication 覆盖了 orders / order_items / messages /
notifications / refund_requests / delivery_exceptions，**唯独漏了 conversations**。
没进 publication 的表，变更事件根本不会发出——"对方把会话标记已读、或新建了一个会话"就不会实时刷新。
migration 只做这一件事（幂等写法，可重复执行）。

**另一处必须守住的细节：实时刷新不能覆盖本地还没写库的改动**

原来的"登录后拉一遍"是**数据库无条件覆盖**同名订单/会话。加了实时推送后这个规则会出事：
商家刚点"接单"（本地已更新、写库还在路上），此时推来一个事件触发重拉，
就会把界面弹回旧状态；更糟的是本地改动会被判定为"已同步"，**再也写不回去**。
处置：合并前先快照"已同步基线"，实时刷新时对**有本地未写库改动**的订单/会话以本地为准；
登录/换账号的首次拉取仍维持"以数据库为准"的原行为（否则跨设备会拿旧本地数据去覆盖新状态）。
