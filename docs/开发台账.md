### 2026-09-27 · 我的修复语句写错了：identities 唯一约束冲突

**现象**：用户重跑 seed 报
`23505 duplicate key value violates unique constraint "identities_provider_id_provider_unique"`，
键值为 `(phone13800000001@jianwei.app, email)`。

**根因（我方失误）**：上一轮加的幂等修正写成了「先插入新身份行 → 再把旧身份行改成同一 provider_id」，
两步都执行完后 `auth.identities` 上出现两行相同 `(provider_id, provider)`，被唯一约束拦下。
正确顺序应为「**先删旧身份行，再插入新行**」。

**更值得记录的是为什么本地没测出来**：校验脚本里的 `auth.identities` 桩表**漏建了两个唯一约束**
（`(provider_id, provider)` 与 `(user_id, provider)`），所以本地跑得通、真实环境才炸。

**处置（三处一起改）**

1. 生成器改为「update 用户邮箱 → delete 该用户身份行 → insert 新身份行」，天然幂等；
2. 校验脚本的 `auth.identities` 桩表补上两个唯一约束，**与真实结构对齐**；
3. 校验脚本新增 **seed 连续执行两遍** 的测试——幂等问题必须靠"跑两遍"才能暴露。

**复验结果**：seed 第 1 遍通过、第 2 遍通过（幂等）、自检 9/26/62/6/3、冒烟测试通过。

**教训（写给自己）**：写幂等修正时必须考虑唯一约束的相互作用；
**桩表与真实结构不一致，会让本地验证给出虚假的安全感**——桩表的保真度和被测脚本同等重要。

### 2026-09-27 · 定位并修复"登录 500"的最终根因（四个 token 列）

**定位手段**：用官方注册接口建了一个探针账号（`codexprobe@jianwei.app`）——它能正常注册并登录；
再让用户执行一段 SQL，把「官方注册的账号 vs 手工插入的演示账号」**逐字段 diff**，差异只剩四处：

| 字段 | 官方注册 | 手工插入 |
|---|---|---|
| `confirmation_token` | `''` | **null** |
| `email_change` | `''` | **null** |
| `email_change_token_new` | `''` | **null** |
| `recovery_token` | `''` | **null** |

**根因**：这几列在 `auth.users` 里「可为空但没有默认值」，手工 INSERT 省略即 null；
而认证服务按非空字符串解析它们，遇到 null 直接抛 500 `Database error querying schema`。
（对照实验：错误密码也报 500 → 崩在"读取账号"阶段而非密码校验；不存在则返回正常的 400。）

**处置**：seed 的 INSERT 显式写这四个空字符串；幂等修正用 `coalesce(...,'')` 修补历史 null（重跑即修复，无需清库）；
本地校验脚本的 `auth.users` 桩表补上这四列，并新增断言"演示账号的这四个 token 列不得为 null"。

**结果**：用户重跑 seed 后，三个演示账号**全部登录成功**，用 token 读 `profiles` 拿到正确的 role/nickname/phone，
触发器建立的资料行完全正确。**第 0 期至此端到端验证通过。**

> 附带发现：Supabase 拒绝「本地部分纯数字」的邮箱（`13900000099@jianwei.app` → `email_address_invalid`），
> 合成邮箱因此定为 `phone{手机号}@jianwei.app`。这一条也曾被误判为根因，实为另一个独立问题。

### 2026-09-27 · 修正 git 代理端口（FlClash 换端口导致推送失败）

**现象**：推送超时改动时报 `Failed to connect to github.com:443 over proxy 127.0.0.1 after 2020 ms`。

**根因**：FlClash 进程仍在运行，但本地端口已从 `7890` 变为 **`10909`**（与 Windows 系统代理 `ProxyServer` 的值一致），
git 里配置的还是旧端口 `7890`，自然连不上。注意端口变化时 FlClash 进程不会退出，**光看进程在不在无法判断代理是否可用**。

**处理**：`git config --global http.https://github.com.proxy http://127.0.0.1:10909`，实测 `git ls-remote` 1.7 秒通过。
同时实测当时**直连也可用**（1.15 秒），说明国内直连 GitHub 是"时通时断"而非完全不通，紧急时可临时绕过代理推送。

**顺带查清**：系统代理端口与 FlClash 混合端口一致，可作为端口变化时的探测依据；已写入 `AGENTS.md` §8.1 第 6 条。
