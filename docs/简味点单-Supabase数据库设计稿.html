一、总览：18 个本地存储域 → 24 张云端表

24数据表
1:1账号↔店铺硬约束
9订单状态
4Realtime 同步通道
四条设计原则
  1. 真源在库：现在散落在 localStorage 的 18 个 key 全部上云，三端读写同一份数据，实时联动。
  2. 快照冗余：订单里冗余菜名、店名、头像、地址快照——商家后来改名改价，不影响历史订单与评价。
  3. 安全靠 RLS：anon key 本就是公开的，所有越权防护由 56 条行级策略 + 3 个服务端 RPC 承担。
  4. 一账号一店铺：shops.owner_id 加 UNIQUE 约束，数据库层面就建不出第二家店。

三、订单状态机（九态 + 三端操作权限，服务端 trigger 兜底）

顾客触发 商家触发 骑手触发 终止态
并发抢单：两个骑手同时点抢单，claim_order() RPC 用一条 UPDATE ... WHERE status='ready' AND rider_id IS NULL 原子完成，只有一人成功，另一人收到「手慢一步」。 非法状态跳转由 guard_order_transition 触发器在数据库层直接拒绝。

五、RLS 权限矩阵（行级安全，anon key 公开也安全）

数据顾客 customer商家 merchant骑手 rider
店铺/菜品/活动只读浏览只能改 owner_id=自己的店只读
订单 orders只能读/取消 customer_id=自己的；只能为自己下单只能读/处理本店订单（接单/出餐/拒单/售后）可读待抢单(ready)与自己接的单；抢单后 rider_id=自己才可推进
地址/收藏/钱包/积分/通知/我的券仅本人全读写不可见他人不可见他人
IM 消息仅参与的会话仅本店相关会话仅自己参与的会话
评价只能为自己订单发评价只能回复本店评价（RPC 限定字段）只读
提现本人记录本店财务记录本人跑单收入
演示店（is_demo=true，owner_id 为空）所有人可读、无人能改；商家自建店 owner_id 自动绑定注册账号，RLS 保证看不到也改不了别人的店。

六、Realtime 实时同步 & Storage 图片存储

Realtime（替换现有 CustomEvent）

orders：顾客订阅自己订单看状态推进；商家订阅本店新单；骑手大厅订阅 ready 待抢单。

messages：IM 新消息即时到达，替代本地轮询。

refund / exceptions / notifications：售后、异常、通知角标实时刷新。

骑手位置：不入库，走 Broadcast 频道 rider:{骑手id}，顾客订单地图直接订阅（位置是瞬时数据，落库无意义且省额度）。

Storage（替换 base64 塞 localStorage）

avatars 头像桶：路径 {uid}/x.jpg，仅本人可写，公开读。

dish-images 菜品桶：路径 {shopId}/x.jpg，RLS 校验是店主才可传。

review-images 评价桶：路径 {uid}/x.jpg，仅本人可写。

三个桶全部公开读（前端 <img> 直接显示）；上传走 supabase-js，不再把图片转 base64 撑爆本地存储。

八、需要你拍板的 5 个设计决策

决策 1 · 登录方式。Supabase 免费版手机号短信要收费，方案是「邮箱+密码」做真实登录，登录页保留「验证码演示入口」：输入任意手机号 + 固定演示码 123456 进入内置演示账号（纯前端 Mock，文档注明预留真实短信接入点）。
建议：按此方案。
决策 2 · 三端账号池。一个 Supabase 账号绑定一个角色（注册时从顾客/商家/骑手端进入即定角色），保持「三端独立、绝不串号」；同一个人想体验三端就注册三个邮箱（如 xxx+customer/@xxx）。
建议：按此方案，与现状一致。
决策 3 · 规格/加料存储。本稿采用规范化子表（spec_groups/options/extras），结构清晰、作品集加分、RLS 随菜品走；备选是直接在 dishes 放 jsonb（前端改动更小但不像正经数据库设计）。
建议：用规范化子表。
决策 4 · 演示店。现有 8 家内置店（饭否、川味轩…）用 seed 脚本写入数据库、标 is_demo=true，所有顾客可见、任何账号不可改；商家自建店与之并列展示（对应现有 getAllShops 合并逻辑）。
建议：按此方案。
决策 5 · 骑手位置。实时位置走 Realtime Broadcast 不落库（省存储、天然实时），订单上只保留最终各节点时间戳。
建议：按此方案。
