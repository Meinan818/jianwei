## 四、技术架构

- **前端**：React 19 + TypeScript + Vite 8，Tailwind CSS v4，shadcn/ui，framer-motion，react-router-dom
- **后端**：Supabase（托管 PostgreSQL + Auth + RLS；**Realtime 第 3 期已启用**；Storage 尚未使用）
- **部署**：GitHub 私有仓库 → Cloudflare Pages 自动构建（推 `main` 即上线）

### 数据层的关键设计（改代码前必须知道）

数据库读取用「**缓存 + 事件 + 实时重拉**」模式，而不是把页面改成异步：

- `src/data/shops-remote.ts` + `src/hooks/useShops.ts` → 店铺 / 分类 / 菜品
- `src/data/orders-remote.ts` + `src/hooks/useOrders.ts` → 订单
- `src/data/messages-remote.ts` + `src/hooks/useMessages.ts` → 会话与消息
- `src/data/realtime.ts`（第 3 期）→ 订阅数据库变更；**不解析推送内容、也不直接改页面状态**，
  收到推送就调用上面三个模块自己的「从数据库重拉」，再派发原有的 CustomEvent

因此：页面代码几乎不用改；断网、未配环境变量、订阅失败时全部静默降级回「手动刷新」，不会白屏。

另有一条必须遵守的细则：**实时重拉不能覆盖本地还没写库的改动**——
合并前先比对「已同步基线」，本地刚做完的操作以本地为准，
否则刚点的「接单 / 出餐」会被数据库里的旧值弹回去，而且再也写不回去。

## 五、本地运行、构建与自检

```bash
npm install
npx vite                        # 本地开发 http://localhost:5173
npx tsc -p tsconfig.app.json    # 类型检查（必须 0 错误）
npm run build:standalone        # 对外部署构建，产物在 dist/client
```

> ⚠️ `npm run build`、`scripts/dev.mjs`、`.spark/` 是原托管平台（妙搭）的包装脚本，
> **平台外不要用**：产物会带平台占位符和水印。对外部署一律 `npm run build:standalone`。

**三个自检脚本**（换人接手后很有用，用法都写在各自文件头）：

| 脚本 | 作用 |
|---|---|
| `supabase/gen/verify_local.mjs` | 本地用 WASM 版 Postgres 把 `supabase/migrations/` 下全部 SQL 跑一遍（每份连跑两遍验幂等），再自检演示数据数量、会话与消息冒烟、演示账号 token 列、以及「订阅的四张表都在 Realtime publication 里」。**不用连真实数据库。** |
| `scripts/e2e-login.html` | 用无头浏览器真实走一遍「启动页 → 顾客端 → 密码登录」的 UI 链路 |
| `scripts/verify-realtime.mjs` | 用演示顾客 + 演示商家两个账号**真连数据库**，验证「顾客改单 → 商家端不刷新即收到」；带对照实验区分"通道不通"与"事件被丢弃"；只做值不变的更新，不污染演示数据 |

**环境变量**：本地放 `.env.local`；线上在 Cloudflare Pages → Settings → Variables and secrets
配置 `VITE_SUPABASE_URL` 与 `VITE_SUPABASE_ANON_KEY`，改完需要重新部署一次才生效。

### ⚠️ 第 3 期配套的一条 SQL（约 1 分钟，建议执行）

在 Supabase 控制台 → **SQL Editor** 里执行
**`supabase/migrations/20260927000000_realtime_conversations.sql`**（整份粘贴执行，可重复执行）。
它只做一件事：把 `conversations` 加进 `supabase_realtime` publication。

不执行也不会崩：订单与消息的实时推送本来就正常（它们本来就在 publication 里），
只有「对方把会话标记已读 / 新建了一个会话」不会实时刷新，要等有新消息时才顺带同步。
执行完 SQL 末尾那段自检查询，应看到四行 `in_realtime_pub = true`。

### 第 3 期的实测结论（含一次被推翻的判断）

用 `scripts/verify-realtime.mjs` 对真实数据库实测：顾客改单后**商家端不刷新就能收到推送**，
而且**不需要**对表设 `REPLICA IDENTITY FULL`。

> 记一笔过程：一开始根据 RLS 策略推断「orders 的读取策略要读多列、默认 replica identity 会让更新事件被静默丢弃」，
> 并据此写了 SQL；随后自己加对照实验真连数据库复测，**推翻了该推断**
> （事件载荷里 `old` 只有 `id`，正说明用的就是默认设置）。
> 所以那条 SQL 已收窄成只补 `conversations`，文件名也改准了。教训：推断要配对照实验。

## 七、已知的坑（都踩过，记这里省时间）

1. **不要用 `.upsert()` 写数据库**：它走的 `ON CONFLICT DO UPDATE` 在 RLS 下会被拒，
   必须「先 INSERT，遇 23505 再 UPDATE」。会话 / 消息 / 订单三处都已按这个写法。
2. **合成邮箱必须带字母前缀**：Supabase 拒绝「本地部分纯数字」的邮箱，
   所以是 `phone13800000001@jianwei.app`，不是 `13800000001@jianwei.app`。
3. **订单 id 与消息 id 是 uuid**（数据库主键要求），界面上的订单号用数据库自增列 `order_seq` 展示。
4. **前端内置演示数据的店铺 id 是 `'1'`~`'8'`，数据库里是 UUID**：写任何关联店铺的数据都必须用数据库 id。
5. **推送 GitHub 依赖代理**：本机走 FlClash，端口变化时 `git push` 会失败；
   当前端口看注册表 `HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyServer`。
   代理没开就别反复重试，先提醒用户。
6. **`supabase/gen/gen_seed.py`** 是演示数据生成器；改动它之后要重新生成 seed 文件。
7. **实时推送的排错顺序**：先确认表**在 `supabase_realtime` publication 里**
   （不在里面 → 事件根本不发出），再用 `node scripts/verify-realtime.mjs` 区分"通道不通"和"事件被丢"。
8. **实时重拉不能覆盖本地未写库的改动**（第四节那条细则），否则用户刚做的操作会被回滚且写不回去。
9. **`verify_local.mjs` 必须先复制到装了 PGlite 的目录再跑**：Node 的 ESM 按**脚本所在目录**
   解析依赖，不认当前工作目录（脚本头部的说明已修正）。
