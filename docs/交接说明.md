## 四、技术架构

- **前端**：React 19 + TypeScript + Vite 8，Tailwind CSS v4，shadcn/ui，framer-motion，react-router-dom
- **后端**：Supabase（托管 PostgreSQL + Auth + RLS；Realtime 与 Storage 已建好但还没用）
- **部署**：GitHub 私有仓库 → Cloudflare Pages 自动构建（推 `main` 即上线）

### 数据层的关键设计（改代码前必须知道）

数据库读取用「**缓存 + 事件**」模式，而不是把页面改成异步：

- `src/data/shops-remote.ts` + `src/hooks/useShops.ts` → 店铺/分类/菜品
- `src/data/orders-remote.ts` + `src/hooks/useOrders.ts` → 订单
- `src/data/messages-remote.ts` + `src/hooks/useMessages.ts` → 会话与消息
- `src/data/realtime.ts`（第 3 期）→ 订阅数据库变更，收到推送就把上面三个模块的重拉函数
  再跑一遍；它本身不解析推送内容，也不直接改页面状态

每个 remote 模块负责「数据库行 ↔ 前端模型」的映射与读写，
对应的 hook 在登录后拉取、在状态变化后回写、在收到实时推送后重拉；**页面代码基本不用改**。
读不到数据时自动退回内置演示数据，所以断网或没配环境变量也不会白屏。

## 五、本地运行与验证

```bash
npm install
npx vite                        # 本地开发 http://localhost:5173
npx tsc -p tsconfig.app.json    # 类型检查（必须 0 错误）
npm run build:standalone        # 对外部署构建，产物在 dist/client
```

> ⚠️ `npm run build`、`scripts/dev.mjs`、`.spark/` 是原托管平台（妙搭）的包装脚本，
> **平台外不要用**：产物会带平台占位符和水印。对外部署一律 `npm run build:standalone`。

**三个自检脚本**（换人接手后很有用）：

- `supabase/gen/verify_local.mjs`：在本地用 WASM 版 Postgres 把 `supabase/migrations/` 下的
  全部 SQL 跑一遍（每份连跑两遍验证幂等），再自检演示数据数量、会话与消息冒烟测试、
  演示账号 token 列、以及第 3 期 Realtime 的两个前提（replica identity / publication）。
  不用连真实数据库（用法见文件头注释）。
- `scripts/e2e-login.html`：用无头浏览器真实走一遍登录流程（用法见文件头注释）
- `scripts/verify-realtime.mjs`：用演示顾客 + 演示商家两个账号真连数据库，
  验证「顾客改单 → 商家端不刷新即收到」；带对照实验区分"通道不通"与"事件被丢弃"，
  只做值不变的更新，不污染演示数据（用法见文件头注释）

**环境变量**：本地放 `.env.local`；线上在 Cloudflare Pages → Settings → Variables and secrets
配置 `VITE_SUPABASE_URL` 与 `VITE_SUPABASE_ANON_KEY`，改完需要重新部署一次才生效。

### ⚠️ 第 3 期（实时推送）上线前你必须做的一步

在 Supabase 控制台 → SQL Editor 里执行
**`supabase/migrations/20260927000000_realtime_conversations.sql`**（整份粘贴执行即可，可重复执行）。
它只做一件事：把 `conversations` 加进 `supabase_realtime` publication。

不执行也不会崩：订单与消息的实时推送本来就正常（实测见下），
只有「对方把会话标记已读 / 新建会话」不会实时刷新，要等有新消息时才同步。
执行完 SQL 末尾那段自检查询，应看到四行 `in_realtime_pub = true`。

**实测结论**（`node scripts/verify-realtime.mjs`，两个演示账号真连数据库互测）：
顾客改单后**商家端不刷新就能收到推送**，且**不需要**对表设 `REPLICA IDENTITY FULL`。
（这条是踩坑记录：一开始推断"orders 的读取策略要读多列、默认 replica identity 会让更新事件被静默丢弃"，
实测推翻了它——事件里 `old` 只有 `id`，说明用的就是默认设置。）

## 七、已知的坑（都踩过，记在这里省时间）

1. **不要用 `.upsert()` 写数据库**：它走的 `ON CONFLICT DO UPDATE` 在 RLS 下会被拒，
   必须「先 INSERT，遇 23505 再 UPDATE」。会话/消息/订单三处都已按这个写法。
2. **合成邮箱必须带字母前缀**：Supabase 拒绝「本地部分纯数字」的邮箱，
   所以是 `phone13800000001@jianwei.app`，不是 `13800000001@jianwei.app`。
3. **订单 id 与消息 id 是 uuid**（数据库主键要求），界面上的订单号用数据库自增列 `order_seq` 展示。
4. **前端内置演示数据的店铺 id 是 `'1'`~`'8'`，数据库是 UUID**：写任何关联店铺的数据都必须用数据库 id。
5. **推送 GitHub 依赖代理**：本机走 FlClash，端口变化时 `git push` 会失败；
   查当前端口：注册表 `HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyServer`。
6. **`supabase/gen/gen_seed.py`** 是演示数据生成器；改动它之后要重新生成 seed 文件。
7. **实时推送排错顺序**（第 3 期实测得出）：先确认表**在 `supabase_realtime` publication 里**
   （不在里面 → 事件根本不发出），再用 `node scripts/verify-realtime.mjs` 区分"通道不通"和"事件被丢"。
   顺带纠正一条常见说法：本项目实测**不需要** `REPLICA IDENTITY FULL`，
   默认设置在跨端更新场景下推送正常（详见第五节与 `scripts/verify-realtime.mjs`）。
8. **实时刷新不能覆盖本地未写库的改动**：合并前要比对"已同步基线"，
   本地刚做完的操作以本地为准，否则会被数据库里的旧值弹回去。
