## 四、技术架构

- **前端**：React 19 + TypeScript + Vite 8，Tailwind CSS v4，shadcn/ui，framer-motion，react-router-dom
- **后端**：Supabase（托管 PostgreSQL + Auth + RLS；**Realtime 第 3 期已启用**；Storage 尚未使用）
- **部署**：GitHub 私有仓库 → Cloudflare Pages 自动构建（推 `main` 即上线）

### 数据层的关键设计（改代码前必须知道）

数据库读取用「**缓存 + 事件 + 实时重拉**」模式，而不是把页面改成异步：

- `src/data/shops-remote.ts` + `src/hooks/useShops.ts` → 店铺 / 分类 / 菜品
- `src/data/orders-remote.ts` + `src/hooks/useOrders.ts` → 订单
- `src/data/messages-remote.ts` + `src/hooks/useMessages.ts` → 会话与消息
- `src/data/realtime.ts`（第 3 期）→ 订阅数据库变更；**不解析推送内容、也不直接改页面状态**，
  收到推送就调用上面三个模块自己的「从数据库重拉」，再派发原有的 CustomEvent

因此：页面代码几乎不用改；断网、未配环境变量、订阅失败时全部静默降级回「手动刷新」，不会白屏。

另有一条必须遵守的细则：**实时重拉不能覆盖本地还没写库的改动**——
合并前先比对「已同步基线」，本地刚做完的操作以本地为准，
否则刚点的「接单 / 出餐」会被数据库里的旧值弹回去，而且再也写不回去。

### 第 3 期的实测结论（含一次被推翻的判断）

用 `scripts/verify-realtime.mjs` 对真实数据库实测：顾客改单后**商家端不刷新就能收到推送**，
而且**不需要**对表设 `REPLICA IDENTITY FULL`。

> 记一笔过程：一开始根据 RLS 策略推断「orders 的读取策略要读多列、默认 replica identity 会让更新事件被静默丢弃」，
> 并据此写了 SQL；随后自己加对照实验真连数据库复测，**推翻了该推断**
> （事件载荷里 `old` 只有 `id`，正说明用的就是默认设置）。
> 所以那条 SQL 已收窄成只补 `conversations`，文件名也改准了。教训：推断要配对照实验。

## 七、已知的坑（都踩过，记这里省时间）

1. **不要用 `.upsert()` 写数据库**：它走的 `ON CONFLICT DO UPDATE` 在 RLS 下会被拒，
   必须「先 INSERT，遇 23505 再 UPDATE」。会话 / 消息 / 订单三处都已按这个写法。
2. **合成邮箱必须带字母前缀**：Supabase 拒绝「本地部分纯数字」的邮箱，
   所以是 `phone13800000001@jianwei.app`，不是 `13800000001@jianwei.app`。
3. **订单 id 与消息 id 是 uuid**（数据库主键要求），界面上的订单号用数据库自增列 `order_seq` 展示。
4. **前端内置演示数据的店铺 id 是 `'1'`~`'8'`，数据库里是 UUID**：写任何关联店铺的数据都必须用数据库 id。
5. **推送 GitHub 依赖代理**：本机走 FlClash，端口变化时 `git push` 会失败；
   当前端口看注册表 `HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyServer`。
   代理没开就别反复重试，先提醒用户。
6. **`supabase/gen/gen_seed.py`** 是演示数据生成器；改动它之后要重新生成 seed 文件。
7. **实时推送的排错顺序**：先确认表**在 `supabase_realtime` publication 里**
   （不在里面 → 事件根本不发出），再用 `node scripts/verify-realtime.mjs` 区分"通道不通"和"事件被丢"。
8. **实时重拉不能覆盖本地未写库的改动**（第四节那条细则），否则用户刚做的操作会被回滚且写不回去。
9. **`verify_local.mjs` 必须先复制到装了 PGlite 的目录再跑**：Node 的 ESM 按**脚本所在目录**
   解析依赖，不认当前工作目录（脚本头部的说明已修正）。
10. **验证线上是哪一版，不要比对 bundle 文件名**：Cloudflare 构建产物的哈希与本地构建不同
    （同一次提交本地 `index-DaF7W2U0.js`、线上可能叫 `index-DdK9-DMk.js`）。正确做法：从线上
    index.html 取 script src，`curl --compressed` 拉该 JS 后 grep 本次改动独有的 console 字符串。
11. **FlClash 开 TUN 模式时推送会失败**：系统代理关闭、无 HTTP 代理端口（核心进程只监听 53 做 DNS），
    git 里配置的代理端口必然连不上。直接 `git -c http.https://github.com.proxy= push` 绕过代理即可。
12. **判断"写库成功"要看返回的行数，不能只看有没有报错**：RLS 的 `using` 子句会把不属于自己的行
    **静默过滤掉**——更新别人家店铺的菜不会报错，只是返回 0 行。所以 `shop-config-remote.ts` 里
    所有 UPDATE / DELETE 都带 `.select('id')` 回读，拿到 0 行就按失败处理（保留本机覆盖、不假装成功）。
13. **本机覆盖层会盖住数据库**：`shopStatus`（localStorage 键 `food_delivery_shop_status`）是"本机优先"的。
    老版本会给**每一道菜**铺一份默认覆盖，于是商家在另一台设备改过之后，这台设备永远看不到新值。
    2h 已改成"只在真的改过时才有记录"、并在写库成功后把字段交还给数据库，同时加了老数据自动清理。
    如果某台设备上仍看不到商家改的值，先清一次该站点的 localStorage 再看。
14. **往 publication 加表之后，Realtime 不是立刻生效的**：2026-09-28 实测——刚在 SQL Editor
    跑完 `20260927010000_realtime_shop_config.sql`（自检 8 行 `in_realtime_pub = true`）时，
    订阅 `dishes` / `shops` **收不到推送**（同时刻 `orders` 推送正常，说明通道本身没坏）；
    **约一分钟后重新建连接订阅，事件就正常送达了**（实测收到 dishes 2 条、shops 1 条）。
    结论：Realtime 服务会缓存 publication 的表清单，新加的表要等它重新读一次（或重连）才推。
    排查时别急着判定"没生效"，等 1 分钟用新连接再试一次。
17. **订单状态白名单不能漏项**：`normalizeOrder` 曾经漏掉 `rejected`（也漏了 `pending_payment`），
    归一化会把拒单**悄悄改回 pending**——表现是"订单还在、仍显示待接单、顾客端什么也看不到"，
    而数据库里留下一条带 `reject_reason` 的 pending 畸形单。现在白名单是 `ALL_ORDER_STATUSES`
    （9 态，与数据库 `order_status` 枚举一一对应），未知状态会打日志而不是静默改写。
18. **商家改"别人的行"必须 update 优先**：`orders` / `refund_requests` / `delivery_exceptions` 的
    INSERT 策略只放行创建者（顾客／上报人），商家插入会先撞 **RLS 42501**（不是主键冲突 23505），
    老写法「先 INSERT 遇 23505 再 UPDATE」把它当成"写失败"直接返回，UPDATE 永远执行不到——
    商家拒单/接单/出餐、售后处理、异常处理全都写不进数据库。
    现已统一走 `upsertByKey()`（先按 key 列 UPDATE，0 行再 INSERT，撞 23505 再补一次 UPDATE）。
20. **购物车是按 skuKey 索引的，不是按菜品 id**：`skuKey = 菜品id__规格__加料`（无规格时形如 `<uuid>____`）。
    菜单上的加减号是按"菜品"显示合计数量的，所以减少时必须先按 `dishId` 找到购物车里的明细、再拿它的
    `skuKey` 去减；直接传 `dishId` 会永远匹配不到（2026-09-28 的 bug：点减号数量不变）。

21. **骑手身份要写 uuid，不能写工号**：`orders.rider_id` 是 uuid 列（指向 `profiles.id`），工号（`R0003`）只用于展示。
    骑手端页面一度把工号当身份传给 `riderClaim`，写库直接被拒 → 抢单在本机看着成功，下一秒被
    「以数据库为准」的刷新打回「待抢单」（和商家拒单是同一类问题）。现在四个骑手页 + `ChatPage` 都用 `user.id`。
    回归脚本 `scripts/e2e-rider.html` 会真跑一遍「抢单 → 确认取餐 → 开始配送 → 确认送达」。
19. **状态变化后要有地方"看得到"**：商家端「已完成」标签原来只匹配 `delivered`，
    订单被拒单/取消后会**从所有标签里消失**（既不在待接单、也不在已完成），
    看起来就像"订单不见了/没生效"。给订单加新终态时，记得同步 `MerchantOrdersPage` 的 `STATUS_MAP`
    与状态文案（`rejected` → 已拒单 · 原因、`cancelled` → 已取消 · 原因）。
15. **订单明细不能每次回写都插一遍**：`order_items` 在本项目里是"下单快照、不可改"（RLS 只有 select / insert
    两条策略），也没有 `(order_id, sort)` 唯一约束。`upsertOrder` 曾经每次回写都 `insert` 一遍明细，
    实测把一笔订单写成 96 条、另一笔 192 条，顾客端与商家端显示成一长串同样的菜。
    现在改成**只在新订单时写明细**，老订单仅在"库里确实没有明细"时补写——不要再改回每次回写都插。    历史脏数据由 `supabase/migrations/20260928000000_fix_order_items_dedupe.sql` 清理
    （**要在 Supabase 控制台 SQL Editor 跑**，应用侧没有 order_items 的删除权限）；
    该脚本还会加 `(order_id, sort)` 唯一索引，以后真再写重了会直接撞冲突而不是静默堆积。
16. **商家端页面靠 `useShopStatus` 触发店铺加载**：只有 `useShops()` 会调用 `ensureShopsLoaded()`，
    而商家端页面一律不调 `useShops()`。触发点因此放在 `useShopStatus` 里；若哪天删掉，
    商家端所有读 `getAllShops()` 的页面都会退回"内置演示店铺"，找不到自己 uuid 的店铺
    （表现为「商品管理」永远停在"店铺数据加载中..."）。
