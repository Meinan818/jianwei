# 后端重写 · 前端模型对账与设计

> 背景（2026-09-27）：用户要求**推翻原有后端资产、重新开发**。
> 起因是交接包里的两个 migration 从未真正执行过——首次执行就连环报错，
> 经本地离线实测找到 3 个真实 bug（详见 `docs/开发台账.md`）。
>
> 本文档是重写的**唯一依据**：以当前前端源码（v60）为事实标准，逐项对账后的结论。
> 对账方法：读取 `src/data/*.ts` 与 `src/hooks/*` 的全部类型定义，逐个字段与 SQL 表结构比对。

## 一、总体结论

原表结构**不是推倒重来的关系**：24 张表里绝大多数与前端模型是对得上的，
真正的问题集中在 4 处「前端有、表里没有」的缺口，加上 3 处工程性问题。
因此重写策略是：**保留已被验证的设计（状态机守卫、销量幂等、钱包原子记账），补齐缺口，重写文件与 seed**。

## 三、必须补齐的缺口（前端有、表里没有）

### 1. `conversations` 缺少三端未读与类型字段（**必须补**）

前端 `IConversation` 有，而表里没有：

- `conv_type`：`'order' | 'shop'`（订单会话 / 店铺咨询会话）
- `unread_customer` / `unread_merchant` / `unread_rider`：**按参与方分别计数**
- 参与方身份快照：`customer_name` / `customer_avatar` / `merchant_name` / `merchant_avatar` / `rider_name` / `rider_avatar`

其中未读三字段是硬需求：AGENTS §4.4 明确要求「未读数有三个方向字段，按会话参与方分别计数」，
而原表只有一个 `messages.is_read` 布尔值，**在数据层面无法表达「同一会话里顾客未读 2 条、商家未读 0 条」**。

### 2. 会话 ID 前缀约定需要在数据层落地

前端会话 id 形如 `shop:<shopId>` / `om:<orderId>` / `or:` / `rm:`。
原表 `conversations.id` 是 uuid 主键，无法承载这个前缀约定。重写时改为 **text 主键**，直接沿用前端的 id 规则，
避免再做一层映射（第 3 期 Realtime 订阅、第 2 期查询都能直接用同一套 id）。

### 3. 演示图片地址是死链（**必须修**）

seed 里 `shops.cover_url` / `dishes.image_url` 全是妙搭平台的存储地址
（形如 `/spark/app/app_17e3cusmabh/runtime/api/v1/storage/object/...`）——脱离平台后无法访问。
前端本地已有 11 张真实图片在 `public/images/`，seed 应改为指向 `/images/xxx.jpg`。
（seed 文件头部原本也注明了这个 TODO，只是从未执行。）

### 4. 登录标识：手机号 vs 邮箱（✅ 已拍板：方案 A）

- 现实：登录页收**手机号**（正则 `^1\d{10}$`），验证码 / 密码 / 注册 / 找回四条路都基于手机号；
  前端账号池也是按 `手机号 + 角色` 存的。
- 交接文档第 1 期写的是「邮箱 + 密码走真实认证」，与 UI 不符。
- Supabase Auth 以邮箱为标识。两种做法：
  - **方案 A（✅ 采用，2026-09-27 用户拍板）**：UI 不变，仍收手机号，前端内部映射为合成邮箱 `{手机号}@jianwei.app` 调 Supabase Auth。
    用户无感知，改动集中在 auth 层；`profiles.phone` 保留真实手机号用于展示。
  - **方案 B**：把登录 UI 改成邮箱。改动大（表单、校验、文案、找回密码全要改），但与演示账号 `demo-*@jianwei.app` 天然一致。

  > ⚠️ **实测补充（2026-09-27）**：合成邮箱**不能是纯数字本地部分**。
  > Supabase Auth 对 `13900000099@jianwei.app` 直接返回 `email_address_invalid`；
  > 用 `abc-test@jianwei.app` 则正常通过校验。因此最终口径是 **`phone{手机号}@jianwei.app`**，
  > 不是文档早期写的 `{手机号}@jianwei.app`。

## 四、工程性问题

1. **`supabase/gen/gen_seed.py` 已失效**：它按「v25 源码」的写法解析 `const IMG_BASE = '...'`，
   而当前源码是 `const IMG_BASE = (import.meta.env.BASE_URL || '/') + 'images/'`，脚本直接抛错跑不起来。
   重写时需决定：修好它，还是改为「seed 文件即事实来源」并在文档里写明。
2. **`src/data/wallet.ts` 是死代码**：全项目无引用，实际使用的是 `src/data/member.ts`。
   重写以 member.ts 为准（老文档若提 wallet 模型，作废）。
3. **迁移脚本不可重复执行**：`init_schema.sql` 里的 `create type` / `create table` 都不带幂等保护，
   中途失败后重跑会报「已存在」。重写时考虑加幂等保护，降低重跑成本。

## 五、重写计划

1. 以本对账为准，写一套**新的 migration**：保留原 24 张表的正确部分，补齐上述缺口，修正顺序与语法问题；
2. seed 重写：图片改本地路径、枚举值一律加引号、演示账号与登录方案保持一致；
3. 用 `supabase/gen/verify_local.mjs` 在本地离线跑通（PGlite），确认自检数字 9/26/62/6/3；
4. 交用户在 Supabase 控制台执行，并做一次真实环境验证；
5. 全过程 tsc / 构建 / 提交 / 推送照旧。

## 六、保留的设计（重写时不动）

原 schema 里有几处是刻意设计的，重写时保留并沿用：

- **订单状态流转的数据库级守卫**（`guard_order_transition` 触发器）：防止前端乱改状态。
- **送达计销量的幂等标记**（`orders.sales_counted`）：重复触发不会重复累加店铺月售。
- **钱包变动的原子记账函数**（`apply_wallet_txn`）：余额与流水在一个事务里完成。
- **抢单的原子函数**（`claim_order`）+ 抢单大厅的部分索引。
- **RLS 策略思路**：三端各自只能读写自己的数据，商家只能改自己的店。
